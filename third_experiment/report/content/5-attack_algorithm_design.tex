本实验的攻击算法按照实验指导书中的思路设计，并与基础实现 \verb|attack\_slow.py| 对应。第 3 节已经说明了 Padding Oracle 攻击的原理，本节不再重复推导公式，而是从算法执行流程的角度说明程序如何一步步恢复目标明文。

\subsection{整体攻击思路}

程序首先将目标密文拆分为
\[
    IV,\ C_1,\ C_2,\ C_3
\]
四个分组，然后从最后一个目标分组开始，逐块恢复对应的中间状态和明文。由于最后一个分组最容易直接观察到原始填充信息，因此程序先处理 $C_3$，再依次处理 $C_2$ 和 $C_1$。

\subsection{基础版算法的主线}

基础版程序按照“先判断原始填充长度，再逐字节向前恢复”的思路进行。对单个目标分组而言，主要步骤如下：

\begin{enumerate}
    \item 取该目标分组真实前一密文分组作为初始参考分组；
    \item 通过逐个修改参考分组的字节，判断原始明文末尾的填充长度；
    \item 根据已知填充长度，先恢复中间状态末尾已经确定的若干字节；
    \item 调整已恢复出的后缀，使它们在解密后变成新的目标填充值；
    \item 枚举当前待求字节，直到服务器返回填充正确，从而恢复新的中间状态字节；
    \item 当整个中间状态恢复完成后，再与真实前一密文分组异或，得到目标明文分组。
\end{enumerate}

这一设计与实验指导书中的推导是一致的，也和第 3 节中的原理说明完全对应。

\subsection{按块恢复的执行过程}

对每个目标分组，程序都会先获得该分组对应的中间状态后缀，再逐步向前扩展。这个过程与原理部分的例子一致：先根据服务器反馈判断原始填充长度，再利用已知后缀去构造新的合法填充，逐字节恢复更多中间状态。等到整个中间状态都恢复完成后，再与真实前一密文分组异或，即可得到当前明文分组。

\subsection{实际提交密文格式}

理论上，Padding Oracle 攻击只需要让服务器检查 $R \parallel C_i$ 解密后的最后一个分组即可。但在本实验环境中，服务器接口接收的是完整密文串，因此程序实际提交的是带有必要前缀的密文。这样虽然提交格式比理论形式更长，但服务器最终检查的仍然是目标块对应的最后一个明文分组，因此不会改变攻击思路。

\subsection{算法复杂度}

对每个待恢复字节而言，最坏情况下需要枚举 256 种可能取值。每个 AES 分组有 16 个字节，因此恢复一个分组最多需要
\[
    16 \times 256 = 4096
\]
次 oracle 查询。

本实验目标密文除 $IV$ 外共有 3 个数据分组，因此理论上的查询上界为
\[
    3 \times 16 \times 256 = 12288.
\]

实际运行时，并不是每个字节都会枚举满 256 次，因此真实查询次数通常小于该上界。与此同时，程序是按块逐步恢复的，因此一旦某个分组恢复完成，就可以立即得到对应的明文结果，便于随时检查程序是否运行正常。
